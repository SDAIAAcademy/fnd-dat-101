Session 1

Loading into constrained tables, and transactions

  • Write table definitions with keys, foreign keys and checks
  • Load a raw file through a staging table and record each rejected row with its reason

01
Constraints

A constraint is a rule the database checks on every row, every time

ConstraintRefusesReturns desk example
PRIMARY KEYa repeated or empty keya second T2
NOT NULLan empty valuea return with no date
REFERENCESa value with no row on the one sidereason R9, which does not exist
CHECKa value outside a stated conditiona refund below zero
What goes wrong. A rule written only in a document is checked by nobody. Written as a constraint, it holds for every program that writes to the table.

Recall Day 1: keys and foreign keys were read from the schema. Today they are written. A foreign key also fixes the order of loading: the one side first.

Step by step

Stage the raw file as text, give each bad row a reason, then insert the rest

1 · Stageevery row as text, numbered in file order
→
2 · Rejecta rule gives each bad row one reason

3 · Insertthe rest, cast to the table's types

Takeaway. Straight into a constrained table, the load stops at the first bad row. Staged, you see them all at once.

Press once per step. The staging table has no constraints at all, and every column is text, so nothing is refused while reading.

A reject rule

CASE gives each row the first reason that applies, so the counts add up

SELECT row_no, return_id,
  CASE
    WHEN return_id = '' THEN 'missing key'
    WHEN ROW_NUMBER() OVER (
      PARTITION BY return_id
      ORDER BY row_no) > 1 THEN 'duplicate key'
    WHEN reason_code NOT IN
      (SELECT reason_code FROM reasons)
      THEN 'unknown reason'
    WHEN TRY_CAST(refund AS DECIMAL(8,2)) < 0
      THEN 'negative refund'
  END AS reason
FROM stg_returns
rowreturn_idreason
1T6
2T6duplicate key
3(empty)missing key
4T7unknown reason
5T8negative refund
6T9

The returns desk (_tools/slide_examples.py, stage-reject).

The first T6 is kept and the second rejected: ROW_NUMBER over the file order decides which copy wins. Say aloud that this is a choice, and the lab makes the same one.

An empty reason means the row is good. The lab's helper keeps the rows with a reason as the reject table.

Transactions

A transaction keeps all its changes or none of them

BEGIN TRANSACTION;
INSERT INTO returns VALUES
  ('T10', 'O-A30', 'R1', 4.00, '2026-05-10'),
  ('T11', 'O-A31', 'R9', 2.00, '2026-05-10'),
  ('T12', 'O-A32', 'R2', 6.00, '2026-05-10');
-- refused: R9 is not a reason
ROLLBACK;
5 → 5
rows of returns, before and after

T10 and T12 were valid, and they are not kept either. Then COMMIT makes every change of a transaction permanent at once.

What goes wrong. Without a transaction, a load that fails halfway leaves orders without their lines, and July's reports count orders with no revenue.

Ask: which is worse, a month not loaded or a month half-loaded? The half-loaded one, because nobody notices it.

The same applies to UPDATE and DELETE: the stretch of lab 4.1 corrects a row and rolls it back.

The load log

Every row read is either loaded or rejected with a reason

FileReadLoadedRejected
returns624

Rejected by reason: missing key 1 · duplicate key 1 · unknown reason 1 · negative refund 1

  • The log is the evidence that nothing was lost silently
  • A rejection upstream changes counts downstream: the items of a rejected return are rejected too

In the lab, three files are logged. Ask participants to predict, before the log runs, why the order lines will show more unknown orders than were planted in the file.

Checkpoint

What does this load log tell you?

A clinic's appointments file: read 500, loaded 480, rejected 15 (12 unknown patient, 3 invalid date).

The load is complete and every row is accounted for
The transaction rolled back 15 rows
Five rows are unaccounted for
The file was loaded twice
Why. 480 + 15 = 495, not 500. Five rows were neither loaded nor rejected: the log is not finished until read equals loaded plus rejected.

Answer: five unaccounted. The usual cause is a rule that gives no reason to a row it still filters out, for example a WHERE in the insert that the reject rule does not mirror.

Session 2

Views that limit what is exposed

  • Mark the personal-data columns of a table
  • Label tables with classification levels under a stated rule
  • Build a view that exposes only what an analyst needs, and test it
02
Personal data

A column is personal data if it can identify a person, alone or with others

Direct identifier

Points to one person by itself: a name, a phone number, an e-mail address.

Indirect identifier

Narrows the group when combined: a date, an area, a key that links all of one person's records.

Neither

Describes a choice or the record, and identifies no one on its own.

The returns desk's callback list: return_id, caller_name, caller_phone, area, received_on, callback_ok. Which is which?

The Personal Data Protection Law treats data that identifies a person directly or indirectly as personal data.

Take answers from the room for the six columns. Name and phone are direct; area and the date are indirect; the return number is indirect, because it links to the order and through it to a person; callback_ok is neither.

The point to land: removing the name does not make a table anonymous.

Minimisation

Give each reader the columns the purpose needs, and no more

  • The law asks that personal data be limited to the minimum necessary for the purpose (PDPL, Article 11, paragraph 3)
  • The Minimum Personal Data guideline adds: restrict access rights to what each role actually needs
  • A purpose is a question: "how many returns per area each week" needs no name and no phone
  • An exact date can often become a week or a month; an exact year, a decade
What goes wrong. "Give them a copy without the names" makes a second table to secure, forget and leak. A view is not a copy.

Both texts are in the README's references. The guideline's point about access rights is the bridge to views: the view is how the rights are narrowed in the database.

Classification

A level says how much harm disclosure would do, and so how the data is handled

LevelImpactUnauthorised disclosure has
Top Secrethighan exceptionally serious and irreparable effect
Secretmediuma serious effect
Restrictedlowa limited negative effect, including on an individual; examples include personally identifiable information and detailed statements of individual transactions
Publicnonenone of these effects

The four levels of the national Data Classification Policy, written for public entities. Data not yet classified is treated as Restricted until it is. In the labs, the grocery delivery company has adopted the levels as its own rule.

Be exact about scope: the policy binds public entities. A private company can adopt the levels, and the case company has; that is its rule, not the law's.

The returns desk's callback list is Restricted: personal data. Its list of reason codes is Public if the company has published it.

Views

A view is a stored query: readers see its columns, never the table behind it

CREATE VIEW returns_for_analysts AS
SELECT return_id,                              -- kept: joins to items; still personal data
       area,
       DATE_TRUNC('week', received_on) AS received_week
FROM callback_list;                            -- no name, no phone, no exact date

-- the test: none of these may appear
DESCRIBE returns_for_analysts;
Grant the view, not the table. The analysts' role reads the view; the table stays with the desk.

Two habits: a comment on every kept column saying why, and a test that the banned columns are absent. The lab runs that test.

The view does not anonymise: the return number still links each row to a person, so the view's output is still Restricted.

Responsible use

Restricted rows never go into a generative AI tool; the schema can

Can go in

What the company has labelled Public: column names and types, the written business rules, an error message, a query with no values from the data.

Stays out

Rows of a Restricted table, a view's output, a sample "just to show the shape", a screenshot of a result.

Rule. Only Public data goes into a generative AI tool. Which descriptions count as Public is the company's own labelling, written down before anyone relies on it.

The rule follows SDAIA's Generative Artificial Intelligence Guidelines for Government (2025), section 3.5, Privacy and Security: employees of government entities enter no data classified Restricted or higher, and use these tools only with data classified Public. The guideline is written for government entities; the company, a private business, applies it as its own rule. The company in the labs has labelled its schema descriptions, its written rules and error messages Public; that labelling is its own rule. Everything in the course is synthetic, but practise the habit as if the rows were real.

Segregation of duties: the person who wants to use the assistant does not decide the label; the data owner does.

Checkpoint

Which view gives the analysts what they need, and no more?

A gym's members table: member_id, full_name, phone, birth_date, branch, joined_on. The analysts count members per branch and per age band.

member_id, branch, age band
member_id, branch, birth_date
member_id, branch, birth_date, joined_on
a copy of the table without full_name
Why. Two counts need the branch and an age band. The key stays only if a join needs it; nothing else serves the purpose.

Answer: the first. Ask whether member_id is needed at all for these two counts: strictly, no. Keep it only if the analysts join to visits.

Query plans and indexes

  • Read the operators of a query plan from the bottom up
  • Find where a filter is applied in a plan
  • Predict when an index changes a plan and when it does not
03
EXPLAIN

A plan is a tree of operators: read it from the bottom up

Seq Scanreturns, filter on the date · reasons
→
Hash Joinon reason_code
→
Hash Group Byby label, sum of refund
→
Projectionthe columns returned
EXPLAIN
SELECT r.label, SUM(t.refund)
FROM returns t JOIN reasons r ON r.reason_code = t.reason_code
WHERE t.received_on >= DATE '2026-05-03'
GROUP BY r.label;

The plan DuckDB prints for this query, drawn left to right (_tools/slide_examples.py, plan-filter). Run it live if there is time: the boxes in the output are the same four steps, bottom to top.

Where the filter is

The engine applies a filter as early as it can, often inside the scan

  • In the returns plan, the date condition appears in the scan of returns, under Filters:
  • Rows that fail it never reach the join: less to match, less to group
  • The numbers after ~ are the engine's estimates, made before running, not counts
  • A filter on the result of a group (HAVING) cannot move down: it needs the groups first
What goes wrong. Reading the estimates as row counts. To count, run the query; to see the shape, read the plan.

Do not show the lab's plan here: participants find the filter in their own plan of the orders query.

Indexes

An index lets a lookup go straight to its rows instead of reading them all

EXPLAIN QUERY PLAN
SELECT * FROM returns
WHERE order_ref = 'O-A15';
-- SCAN returns

CREATE INDEX ix_returns_order
  ON returns (order_ref);
-- the same lookup:
-- SEARCH returns USING INDEX
--   ix_returns_order (order_ref=?)
  • SCAN: every row is read and tested
  • SEARCH: the index leads to the matching rows
  • A total over the whole table stays a SCAN with or without the index

SQLite, from Python's standard library (_tools/slide_examples.py, index-scan-search). No timings: the plan's shape is what is stable.

Why SQLite: its plan says SCAN or SEARCH in one line, which makes the change visible. DuckDB, built for analysis, mostly reads whole columns and uses its indexes for keys and constraints.

When it helps

An index helps a query that picks few rows by the indexed column

Query on returns, index on order_refPlanWhy
WHERE order_ref = 'O-A15'searchan exact value of the indexed column
SUM(refund) over all returnsscanevery row is needed anyway
WHERE order_ref LIKE '%15'scana pattern starting with % has no place to jump to
WHERE reason_code = 'R1'scannot the indexed column
Takeaway. Analytical queries read most of a table, so they rarely gain from an index. Lookups do.

A two-column index is used from its first column: an index on (area, received_on) helps "area X since May", not "everything since May". The lab's stretch shows it.

Session 4

Testing queries against known answers

  • Build a small fixture and work out the expected answer by hand
  • Write a test that compares a query's result with the expected rows
  • Classify a failing generated query: fan-out, wrong grain or a missing business rule
04
Testing

A query is right when it matches an answer worked out by hand

1 · Fixturetables small enough to print
→
2 · Expectedthe answer on paper, from the rule
→
3 · Runthe query on the fixture
→
4 · Comparepass, or find out why
Takeaway. The expected answer must not come from SQL: another query can share the mistake.

Ask why the full data will not do: nobody knows its right answer without a query. The fixture must hold the hard cases: a failed attempt, a returned order, a cancelled line, an empty discount.

Why queries fail

Most wrong totals are one of three mistakes

Fan-out

A join repeats rows. Returns joined to inspections: T2's refund counted twice.

Wrong grain

The right sum at the wrong level: an average per item when the question is per return.

Missing rule

Well formed, but a business rule is left out: the desk's rule says a return with no refund counts as 0.

Each has a signature. Fan-out: the total is too high, often by a pattern that matches repeat rows. Grain: an average that is too small or too large by the number of items. Missing rule: a small difference that a rule explains.

A test that fails

The average refund per return: the generated query against the rule

17.44
AVG(refund): skips T4, whose refund is empty
13.95
by hand, with T4 as 0: 69.75 over 5 returns

Test: FAIL. Kind: missing rule. The fix is one COALESCE; finding it took the rule and a fixture.

The returns desk (_tools/slide_examples.py, test-avg-refund).

Day 2's NULL lesson in a new place. Ask: which would a reader of the report have noticed? Neither number looks wrong.

Checkpoint

A generated query passes its test. What does that show?

A pharmacy fixture has six orders, none with two delivery attempts. The generated revenue query matches the hand-checked answer.

The query is correct on the full data
It follows the rule on the cases the fixture holds; repeat attempts are untested
Nothing: generated queries cannot be trusted
The fixture is too small to mean anything
Why. A test proves the cases in the fixture. Fan-out over repeat attempts needs a fixture with repeat attempts.

Answer: the second. The fix is to add an order with a failed attempt to the fixture and run the test again.

Wrap-up

Three things to keep from Day 4

Refuse and account

Constraints refuse bad rows; the log accounts for every row read.

Expose the minimum

A view per purpose, tested; Restricted rows stay out of assistants.

Prove it by hand

A query is right when it matches an answer worked out on a fixture.
