Session 1

Join fan-out and double counting

  • Detect fan-out by counting rows before and after a join
  • Aggregate to the right grain before joining
  • Explain a wrong total from the grain of each table it joined
01
Fan-out

A join to a many side repeats every row of the one side

return_idrefundinspection
T112.00pass
T230.50pass
T230.50fail
T519.00pass
  • T2 was inspected twice, so its refund now sits on two rows
  • Every column of returns is repeated, not only the key
  • Nothing warns you: the query runs, the numbers look plausible

This is yesterday's inner join slide, with the refund column added. Ask what SUM(refund) over these four rows gives before showing the next slide.

Double counting

Every sum over a fanned-out join grows

92.00
SUM(refund) after the join
61.50
the refunds of the inspected returns

30.50 counted twice. And T3 and T4 are gone: the join also drops rows with no partner. A fanned-out sum can be too high and too low at once.

The returns desk (_tools/slide_examples.py).

The lab shows the same double effect on the delivery tables, with real money. Do not quote the lab's figures here.

Detect it

Count rows before and after every join

SELECT (SELECT COUNT(*) FROM returns)              AS before,
       (SELECT COUNT(*) FROM returns t
          JOIN inspections i ON i.return_id = t.return_id) AS after;
-- before 5, after 4: rows were dropped AND repeated
  • After > before: some rows repeat
  • After < before: some rows lost their partner
  • Equal is not proof: drops and repeats can cancel out, as they nearly do here

The last bullet is the reason for the next slide: the reliable check is the grain, not the count alone.

The fix

Bring each side to the grain of the question before joining

WITH insp AS (                       -- one row per return
  SELECT return_id, COUNT(*) AS inspections
  FROM inspections GROUP BY return_id
)
SELECT SUM(t.refund), SUM(insp.inspections)
FROM returns t
JOIN insp ON insp.return_id = t.return_id;
-- 61.50 and 4: one row per return on both sides
Or filter instead of joining. WHERE return_id IN (SELECT ...) or EXISTS keeps each return once.

Two patterns: aggregate the many side to the one side's grain, or use the many side only as a filter. Question 16 needs the second, question 17 the first.

A tempting shortcut

SUM(DISTINCT ...) hides fan-out by accident, and breaks on equal values

Looks right here

SUM(DISTINCT refund) on the joined rows gives 61.50: T2's repeat collapses.

Wrong tomorrow

Two different returns with a refund of 12.00 collapse into one. The total is short, and nothing says so.

Rule. DISTINCT removes duplicate values, not duplicate rows of the grain you meant. Fix the grain instead.

Assistants often reach for DISTINCT when a total looks too large. Lab 4.4 tests ten queries with mistakes of this family.

The habit

Before every join, write the grain of both sides and of the result

LeftRightResultSum left?
returnreasonreturnyes
returninspectioninspectionno
returnreturn (aggregated)returnyes

Each grain is "one row per ..." the word in the cell. "Sum left?": is it safe to sum the left side's money after the join?

Ask participants to write these three grains as comments above their queries in today's lab. The capstone rubric rewards it.

Checkpoint

Why is the total fee too high?

A clinic sums appointment fees after joining appointments (one row per appointment) to reminders (one row per reminder sent). Some appointments got three reminders. The total is 40% above the ledger.

Fees left NULL are counted as zero
The join drops appointments with no reminder
Fees are rounded to two decimals
Each fee is repeated once per reminder
Why. After the join the grain is the reminder: an appointment with three reminders carries its fee three times.

Answer: repetition per reminder. Point out that the second option is also true but moves the total the other way.

Session 2

Subqueries and common table expressions

  • Use a subquery in WHERE and in FROM
  • Write a query as a chain of common table expressions
  • Check each step of a chain before trusting the last
02
Subqueries

A subquery is a query inside another, used as a value, a list or a table

WhereReturnsReturns desk example
In WHERE x > (...)one valuerefunds above the average refund
In WHERE x IN (...)a listreturns that were inspected
In FROM (...)a tableitems per return, then their average

The first form must return exactly one value, or the engine refuses. Ask what WHERE refund > (SELECT AVG(refund) FROM returns) keeps: T2 and T5 (above 17.44).

Per row

A correlated subquery is evaluated for each row of the outer query

SELECT t.return_id, t.refund
FROM returns t
WHERE t.refund > (SELECT AVG(r.refund)
                  FROM returns r
                  WHERE r.reason_code = t.reason_code);  -- the average of its own reason
  • The inner query refers to t, the row being tested
  • "Above the average of its own group" is the typical use
  • The same answer can be written as a join to a grouped table: often clearer

This is the shape of question 18 on another table. The lab's solution uses the grouped-table form; both pass the checker.

Common table expressions

WITH names each step, so a long answer reads top to bottom

WITH items AS (                    -- step 1: one row per return
  SELECT return_id, SUM(qty) AS units
  FROM return_items
  GROUP BY return_id
)
SELECT AVG(units) FROM items;      -- step 2: 3.0 units per return
Read it as a recipe. Each name is a table you could look at on its own. Several steps are separated by commas: WITH a AS (...), b AS (...).

A CTE changes nothing the engine can do that a subquery cannot; it changes what a reader can check. That is the point for the capstone, where a reviewer must follow each answer.

The method

Run each step before you trust the last one

1 · First step aloneselect from it; look at 5 rows; count them
→
2 · Its grainone row per what? is a key unique?
→
3 · Add the next stepand repeat
→
4 · The final selectcompare with your prediction

Demonstrate on the returns desk: replace the final SELECT with SELECT * FROM items, read the five rows, then put it back.

Business rules

Some rules live outside the schema, and the query must carry them

What the schema says

Columns, types, keys, a status column with three values.

What it does not say

Which statuses count as revenue, what an empty discount means, which date books the money.

The finance controller keeps that in data/revenue_rule.md. A query that ignores it runs without error and returns a number nobody in finance would sign.

Ask the room to read the rule now, in two minutes. Ask: which of its six points could a query break without any error message? (All of them.)

Session 3

Partitions, ranking, lag and lead

  • Write a window with a partition and an ordering
  • Choose between ROW_NUMBER, RANK and DENSE_RANK at ties
  • Compare a row with the one before it using LAG
03
Window functions

A window computes over related rows and keeps every row

GROUP BY

Five returns in, three rows out: one per reason. The detail is gone.

OVER (...)

Five returns in, five rows out, each with a value computed from its group.

SELECT return_id, reason_code, refund,
       SUM(refund) OVER (PARTITION BY reason_code) AS reason_total
FROM returns;

T1 and T3 both show 20.25 beside their own refunds. Ask what share of its reason's refunds T1 is: 12.00 / 20.25. That division needs the detail and the total on one row, which is what windows are for.

Sources: DuckDB window functions documentation (in course sources).

The two clauses

PARTITION BY says which rows belong together; ORDER BY says in what sequence

ClauseQuestion it answersWithout it
PARTITION BY regionWhose rows are compared?all rows form one window
ORDER BY dayWhich row comes before which?ranks and LAG have no meaning
Say the partition in a comment. "-- partition: one ranking per region, so ..." The window checker of the labs asks for exactly this.

The outcome's evidence asks for each partition explained in a comment. Make it a habit from the first window they write.

Ranking

ROW_NUMBER, RANK and DENSE_RANK differ only at ties

product (units)ROW_

Returned units per product at the returns desk, ordered by units from the most.

"Top two" with ROW_NUMBER picks X-101 and X-412 here, but between X-118 and X-205 it would pick by chance without a tie-breaker. RANK keeps ties together and skips the next place.

Top N per group

Rank inside each partition, then keep the first places

WITH ranked AS (
  SELECT reason_code, return_id, refund,
         RANK() OVER (PARTITION BY reason_code ORDER BY refund DESC) AS place
  FROM returns
)
SELECT * FROM ranked WHERE place = 1;   -- the largest refund of each reason
What goes wrong. WHERE RANK() OVER (...) = 1 is refused: windows are computed after WHERE. Rank in one step, filter in the next, or use QUALIFY.

QUALIFY is supported by DuckDB and some other engines; the two-step form works everywhere. The stretch of lab 3.3 asks for both.

Ask what would change if each return belonged to a courier and the question were "days since that courier's previous return": PARTITION BY courier.

Checkpoint

Which ranking keeps every tied product in a "top three"?

Sales per product in each region: in the West, two products tie for third place. The manager wants both shown, and the next product, if any, to be fifth.

ROW_NUMBER() and place <= 3
DENSE_RANK() and place <= 3
RANK() and place <= 3
ORDER BY sales DESC LIMIT 3
Why. RANK gives ties the same place and skips the next one, as asked.

Answer: RANK. DENSE_RANK is right when the manager wants "the top three different sales values".

Comparing periods

For week-on-week change, aggregate to weeks first, then LAG

1 · Daily rowsone row per store and day
→
2 · Weekly totalsGROUP BY store, week
→
3 · LAG over weeksPARTITION BY store ORDER BY week
→
4 · Changethis week minus the previous
What goes wrong. A first or last week with fewer days looks like a fall or a jump. Say so beside the number, or leave partial weeks out.

The data of the labs starts on a Thursday and ends on a Tuesday: drill 4 shows both partial weeks. The participants should notice them unprompted; if not, point at the first row.

Frames

The frame decides which rows a moving average uses

FrameMeans
ROWS BETWEEN 6 PRECEDING AND CURRENT ROWthis row and the six rows before it
RANGE BETWEEN INTERVAL 6 DAYS PRECEDING AND CURRENT ROWevery row whose date is within the last seven days

They agree when every day has exactly one row. They part when a day is missing.

The default frame with an ORDER BY is "from the first row to the current one" (with peers), which is why SUM gives a running total without a frame clause.

Sources: DuckDB window functions documentation (in course sources).

Missing days

With a missing day, ROWS reaches too far back; RANGE does not

received_onday's refunds2 rows2 days
2026-05-0242.5042.5042.50
2026-05-038.2525.3825.38
2026-05-040.004.134.13
2026-05-0619.009.5019.00

No return arrived on 5 May. "2 rows" averages 6 May with 4 May; "2 days" averages only 6 May, the one day in its window that has a row.

A two-day window keeps the table small; the lab does the same with seven days and a store closed for three days. Neither frame treats the missing day as zero; a calendar table does (the stretch).

Checkpoint

Which seven-day average is right after a closed weekend?

A pharmacy's daily sales table has no rows for two closed days. For each day, the report wants the average daily sales of the days that had sales within the last seven calendar days, that day included.

AVG OVER (ORDER BY day RANGE BETWEEN INTERVAL 6 DAYS PRECEDING AND CURRENT ROW)
AVG OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)
AVG OVER (PARTITION BY day)
AVG with GROUP BY week
Why. RANGE with an interval selects rows by date, so the window always covers seven calendar days.

Answer: RANGE. Note that the question says "days with sales": if it wanted closed days as zeros, neither frame would do without a calendar.
