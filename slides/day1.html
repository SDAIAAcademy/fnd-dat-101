01
What a table is

A table holds rows of one kind, each with the same columns

return_idorder_refreason_coderefundreceived_on
T1O-A11R112.002026-05-02
T2O-A12R230.502026-05-02
T3O-A15R18.252026-05-03
T4O-A15R3NULL2026-05-04
T5O-A20R219.002026-05-06

The company's returns desk: the returns table. The slides use this department; the labs use the delivery tables.

Unlike a sheet. No merged cells, no totals row, no colour that means something. Every fact sits in a column with a name.

Contrast with a spreadsheet: a sheet lets anything go in any cell. A table promises that each row is one returned parcel and each column one fact about it.

Point at T4: the refund is NULL, unknown, because the refund has not been decided yet. Day 2 spends a session on that word.

Types

Every column has a type, and the type decides what fits

TypeHoldsExample
VARCHARtext'R1'
INTEGERwhole numbers3
DECIMAL(8,2)exact amounts, two decimals30.50
DATE, TIMESTAMPa day; a day and a time of dayDATE '2026-05-02'
BOOLEANtrue or falsetrue
What goes wrong. An amount stored as text sorts as text: '9.00' comes after '30.50'. A date stored as text cannot be compared with a range.

Money is DECIMAL, never a floating-point number: 0.1 plus 0.2 is not exactly 0.3 in floating point, and finance notices.

Ask: which column of the returns table would break first if it were stored as text? (received_on: ranges stop working.)

Keys

A key is a column, or a set of columns, that names exactly one row

A single-column key

return_id in returns: no two returns share it. Declared as PRIMARY KEY, the engine refuses a second T3.

A composite key

(return_id, item_no) in return_items: a return has several items, so the return alone does not name an item; the pair does.

Not a key. order_ref looks like an identifier, but one order can be returned twice: O-A15 appears in T3 and T4.

Ask the room to find the repeated order reference on the previous slide before you show the callout.

The point for the lab: a column called something_id is a candidate, not a proof. The proof is a count.

Proof, not belief

Test a candidate key by counting rows and distinct values

SELECT COUNT(*)                  AS n_rows,
       COUNT(DISTINCT order_ref) AS n_refs
FROM returns;
-- n_rows 5, n_refs 4
  • Equal numbers: no value repeats, the candidate holds
  • Fewer distinct values: some value repeats, not a key
  • For a pair, count the rows of SELECT DISTINCT a, b: 8 pairs for 8 rows of return_items
Habit. Before you trust a key, count. It takes one query.

Run it live on the returns desk if you have the slide examples open (labs/_tools/slide_examples.py prints these numbers).

Do not show the counts of the delivery tables: lab 1.1 asks for them.

Between tables

A foreign key points at a row that must exist in another table

return_itemsreturn_id T5
→
returnsrow T5 must exist
→
reasonsits reason_code R2 must exist

Declared with REFERENCES returns (return_id), an item for a return that does not exist is refused. Without it, the item would sit in the table, joined to nothing, and every total would quietly miss it.

A foreign key is a promise about two tables at once. It is why the order of loading matters on Day 4: the one side first, then the many side.

Constraints

Constraints refuse rows that make no sense, before anyone queries them

NOT NULL

The value must be there: every return has a received date.

PRIMARY KEY, UNIQUE

No two rows share the value.

REFERENCES

The value exists in the other table.

CHECK

A rule on the value: qty > 0, refund >= 0.

Type

Only that kind of value: no text in a date.

The message

A refusal names the rule it broke. Read it.

Demo on the returns desk: INSERT INTO return_items VALUES ('T1', 2, 'X-999', 0). The engine answers "CHECK constraint failed" and names the expression. Then try a second ('T1', 1, ...) and read the key violation.

Sources: DuckDB constraints documentation (in course sources).

Session 2

Grain and cardinality

  • State the grain of a table in one sentence
  • Confirm a grain with a counting query
  • Measure a one-to-many relationship and name its maximum
02
Grain

The grain is what one row stands for

returns

One row per returned parcel

return_items

One row per item inside one return

inspections

One row per inspection of one return; a return can be inspected twice

Say it in one sentence. "One row per ..." If you cannot finish the sentence, you cannot sum the table safely.

Grain is the single most useful word of the course. Every wrong total on Day 3 is a grain mistake.

Ask: what is the grain of a monthly sales report? (One row per month, or per month and store: the report must say which.)

Writing it down

A good grain sentence names the thing and the one it belongs to

VaguePrecise
"Items"One row per item inside one return
"Inspection data"One row per inspection of one return, on one day
"Refunds by reason"One row per reason code, with the sum of refunds

The precise sentence tells you the key: the thing, plus whatever tells two of them apart.

Read the vague column aloud and ask the room to improve each before revealing the precise one.

Cardinality

Cardinality says how many rows of one table meet one row of another

One to one

Each return has exactly one decision letter.

One to many

Each return has one or more items.

Many to many

Products and returns: resolved through return_items.

Write it as a range. "Items per return: 1..3" says more than "one to many": it gives the fewest and the most.

The range notation is what lab 1.2 asks for. The fewest is often 0, and 0 is where queries go wrong.

Measure it

Group the many side by the key of the one side, then read the smallest and largest group

SELECT MIN(n) AS fewest, MAX(n) AS most
FROM (SELECT return_id, COUNT(*) AS n
      FROM return_items
      GROUP BY return_id);
-- fewest 1, most 3
What goes wrong. This query only sees returns that have items. A return with no item would not appear in the inner result, so "fewest" can never read 0 here.

Walk through the inner query first: it is a small table of its own, one row per return. Then the outer query reads two numbers from it.

The zero case

To see the zeros, count from the one side

SELECT r.reason_code,
       COUNT(t.return_id) AS returns
FROM reasons r
LEFT JOIN returns t
  ON t.reason_code = r.reason_code
GROUP BY r.reason_code;
reason_codereturns
R12
R22
R31
R40

Reasons to returns: 0..2. Grouping returns alone would have said 1..2 and hidden R4.

The LEFT JOIN is a preview of Day 2; today it is enough to know it keeps every row of the left table. COUNT of a column counts only the rows where it is not NULL, which is why R4 shows 0.

03
Normal forms, in brief

Normalised tables store each fact once

FormThe rule, in plain wordsReturns desk example
FirstOne value per cell; no lists inside a cellItems in their own rows, not "X-101, X-205" in one cell
SecondEvery column depends on the whole keyThe reason label is not in return_items: it depends on the return, not the item
ThirdNo column depends on another non-key columnThe label lives in reasons, reached through reason_code

Keep this brief: the entry asks for normal forms "in brief". The idea to keep is the third column: each fact has one home.

Sources: SDAIA Academic Programs Standards Framework, DM-Relational topics include normalisation motivation (in course sources).

Why it matters

A fact written many times can disagree with itself

Reason label copied onto every item

Rename R2 from "wrong item" to "wrong product". Change 3 of the 5 rows that carry it and the table now holds both labels for the same code.

Label stored once in reasons

Change one row. Every query that joins to reasons sees the new label at once.

The update anomaly. It needs no bug: only a partial fix, which is what busy people make.

Lab 1.3 makes this happen on purpose with a store's region in a wide table.

The other side

Analytical tables are wide on purpose

  • Read far more than written: an analysis reads millions of rows and changes none
  • Fewer joins for every question: the category and region already sit on the line
  • Built from the normalised source on a schedule, never edited by hand
  • Columnar engines store each column apart, so unused wide columns cost little to read
The rule. A wide table is a copy. When it is wrong, fix the source and rebuild the copy.

This is why analysts and database designers argue: both are right for their workload. The entry asks why analytical tables are wider; this slide is that answer.

Where the engine runs

An embedded engine runs inside your program; a server runs apart and you connect to it

Embedded

  • A library in your Python process
  • The database is a file
  • Nothing to install or administer
  • One writer at a time, on one machine

Client-server

  • A separate server process, often another machine
  • Accounts, permissions, network
  • Many users reading and writing at once
  • Someone runs and backs it up

The SQL you learn here runs on both, with small differences of dialect.

SQLite's own documentation describes it as serverless: no separate server process to install or manage. DuckDB's documentation says it runs embedded within a host process.

Sources: SQLite "SQLite Is Serverless"; DuckDB "Why DuckDB" (in course sources).

The tool slot

Two embedded engines, built for different work

Analytical engine (DuckDB)Transactional engine (SQLite)
Built forScans and aggregates over many rowsMany small reads and writes
StoresColumn by column, processed in batchesRow by row
In this courseEvery lab on the full dataLab 1.3 on the mini tables; lab 4.3 for indexes

Examples of a capability, not endorsements. Either engine is free and runs on a laptop processor.

DuckDB's documentation describes a columnar, vectorised execution engine. SQLite ships inside Python's standard library, which is why lab 1.3 needs no install for it.

Sources: DuckDB "Why DuckDB"; SQLite documentation (in course sources).

04
How a query is read

You write SELECT first, but the engine reads FROM first

1 · FROMwhich table
→
2 · WHEREwhich rows
→
3 · SELECTwhich columns, computed how
→
4 · ORDER BY, LIMITin which order, how many
Read in this order when you predict a result: start with the table, then cross out rows, then pick columns.

Day 2 adds GROUP BY and HAVING between WHERE and SELECT. Tell the room this now so the order does not change on them later.

Filters

WHERE keeps the rows for which the condition is true

SELECT return_id, refund
FROM returns
WHERE reason_code = 'R1'
  AND refund >= 10;
-- T1 12.00
  • Comparisons: =, <>, <, >=
  • Combine with AND, OR, NOT; use brackets when you mix them
  • A list: reason_code IN ('R1', 'R2')
  • Text is in single quotes; column names are not

Ask the room to predict the result before you reveal the comment line. T3 is R1 too, but its refund is 8.25. T4's refund is NULL: Day 2 explains why it is not kept by either >= 10 or < 10.

Text

= matches exactly; LIKE and ILIKE match a pattern

ConditionKeeps
product_ref = 'X-101'exactly that code
product_ref LIKE 'X-1%'codes starting with X-1; % is any run of characters
label ILIKE '%item%'"item" anywhere, in any letter case
LOWER(label) = 'late'"late", "Late", "LATE"
What goes wrong. In DuckDB LIKE is case-sensitive: LIKE '%Item%' misses "wrong item". SQLite ignores case for plain letters: the same query behaves differently in another engine.

ILIKE is supported by DuckDB and several other engines but not by every one; LOWER on both sides works everywhere.

Dates and times

Filter a period with a half-open range: from the first day, up to but not including the next

SELECT COUNT(*)
FROM returns
WHERE received_on >= DATE '2026-05-02'
  AND received_on <  DATE '2026-05-04';
-- 3 returns: T1, T2, T3
What goes wrong. On a timestamp column, BETWEEN '2026-05-02' AND '2026-05-03' stops at the first instant of 3 May and drops the rest of that day.

received_on is a DATE, so here BETWEEN would happen to work. The delivery tables use TIMESTAMP for ordered_at and attempted_at, where it does not. The stretch of lab 1.4 asks why.

Sorting

ORDER BY needs a tie-breaker before LIMIT can be trusted

SELECT return_id, received_on
FROM returns
ORDER BY received_on DESC,
         return_id
LIMIT 2;
-- T5 2026-05-06
-- T4 2026-05-04
  • DESC from the highest; ascending is the default
  • T1 and T2 share a date: without return_id their order is not defined
  • LIMIT n keeps the first n rows after sorting

Without a tie-breaker, a top ten can differ between runs or engines when two rows tie at the tenth place. The checker of the twenty questions expects the stated order exactly.

Expressions

An expression computes a new value for each row

SELECT return_id,
       COALESCE(refund, 0) AS refund_or_zero,
       date_trunc('month', received_on) AS month,
       UPPER(reason_code) AS code
FROM returns;
  • Arithmetic: qty * price
  • COALESCE(x, 0): x, or 0 when x is NULL; T4 shows 0.00
  • date_trunc('month', d): the first day of d's month
  • AS name names the new column
What goes wrong. refund - 1 on T4 is NULL, not -1: anything combined with NULL is NULL.

COALESCE is the tool lab 1.4 needs for a line value with an empty discount. Use refund here, never the lab's discount column.

The habit of the course

Write your prediction before you run the query

How many rows?

One, a handful, about a sixth of the table

Roughly what value?

An order of magnitude, a sign, a range

Which first row?

After the sort you asked for

Why. A result that surprises you is either a discovery or a bug. Without a prediction you cannot tell that you were surprised.

Predictions are written with the assistant off: the entry's AI policy. They are part of the answer file and the trainer reads them, but they are not marked right or wrong.

Checkpoint

Which filter counts every inspection made in May 2026?

The returns desk stores inspected_at as a TIMESTAMP. You need every inspection of May 2026, including those late on 31 May.

inspected_at BETWEEN '2026-05-01' AND '2026-05-31'
inspected_at LIKE '2026-05%'
inspected_at >= '2026-05-01' AND inspected_at < '2026-06-01'
inspected_at >= '2026-05-01' AND inspected_at <= '2026-06-01'
Why. The half-open range keeps all of 31 May and nothing of 1 June, whatever the time of day.

Answer: the half-open range. The LIKE option is a spreadsheet habit; it fails silently or with a type error on a real timestamp column.
