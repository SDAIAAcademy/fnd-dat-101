Session 1

CASE expressions and set operations

  • Write a CASE expression that sorts rows into bands
  • Count by condition with CASE inside an aggregate
  • Combine two result sets with UNION, INTERSECT or EXCEPT
01
CASE

CASE turns a rule into a column

SELECT return_id, item_no, qty,
  CASE WHEN qty = 1  THEN 'single'
       WHEN qty <= 3 THEN 'few'
       ELSE 'many'
  END AS band
FROM return_items;
  • Branches are tried in order; the first true one wins
  • ELSE catches the rest; without it, the rest is NULL
  • Every branch returns the same type
What goes wrong. Put qty <= 3 first and a quantity of 1 becomes "few".

Ask the room to band the 8 items of the returns desk by hand: 4 single, 3 few, 1 many (printed by _tools/slide_examples.py).

Counting by condition

A CASE inside SUM counts the rows that meet a condition

SELECT reason_code,
       SUM(CASE WHEN refund >= 15 THEN 1 ELSE 0 END) AS large,
       COUNT(*) FILTER (WHERE refund < 15)            AS small
FROM returns
GROUP BY reason_code;
  • Two counts side by side, from one pass over the table
  • FILTER (WHERE ...) says the same thing more briefly where the engine supports it
  • A refund that is NULL is neither large nor small: count it on purpose if it matters

This is the shape of question 6, on another table and another condition. Do not write question 6 on the board.

Set operations

UNION, INTERSECT and EXCEPT combine whole result sets

UNION

In either set, duplicates removed. UNION ALL keeps them.

INTERSECT

In both sets.

EXCEPT

In the first set and not in the second.

SELECT product_ref FROM return_items WHERE return_id IN ('T1', 'T2')
INTERSECT
SELECT product_ref FROM return_items WHERE return_id = 'T5';
-- X-101, X-205: products returned in both groups

Both sides must return the same number of columns, of matching types. The sets compare whole rows.

The catch

Set operations compare whole rows, so choose the columns first

Too many columns

SELECT * on both sides: two different returns never match, so EXCEPT takes nothing away.

The column the question is about

SELECT product_ref on both sides: the comparison is between products, as asked.

Habit. Say "a set of what?" before writing either side.

Question 7 is a set of customers, which is why its two sides select only the customer id.

UNION or UNION ALL

UNION removes duplicates; UNION ALL keeps every row

You wantUse
A list of distinct products returned in May or JuneUNION
All return items of May and June, to sum quantitiesUNION ALL: duplicates are real items
What goes wrong. UNION under a sum silently merges two identical items of different returns, and the total shrinks.

The notebook of lab 2.1 shows both counts on the real tables after question 7.

Session 2

NULL and three-valued logic

  • Predict the rows a comparison with NULL keeps
  • Use IS NULL, COALESCE and IS DISTINCT FROM on purpose
  • Explain why NOT IN with a NULL returns no rows
02
NULL

NULL means unknown: not zero, not empty text, not false

Unknown

T4's refund has not been decided.

Not applicable

A line with no discount, in some designs.

Not recorded

A customer who gave no region.

One marker, several meanings. The schema rarely says which. The business rule does: the finance rule of this course says an empty discount means none.

The point: NULL is a placeholder for a missing value, and the question decides how to treat it. Day 3's revenue rule settles it for discounts.

Three-valued logic

A comparison with NULL is neither true nor false: it is unknown

Condition on T4 (refund NULL)ResultKept by WHERE?
refund = 12.00unknownno
refund <> 12.00unknownno
refund = NULLunknownno
refund IS NULLtrueyes

WHERE keeps a row only when its condition is true.

So refund <> 12.00 keeps 3 of the 5 returns, not 4: T4 drops out. And refund = NULL keeps none. Both numbers come from the slide examples script.

Combining unknowns

AND, OR and NOT carry the unknown through

AND

false AND unknown = false
true AND unknown = unknown

OR

true OR unknown = true
false OR unknown = unknown

NOT

NOT unknown = unknown

What goes wrong. NOT (refund = 12.00) does not bring T4 back: the NOT of unknown is still unknown.

Work one row through each operator on the board. Lab 2.2 has twelve such predictions; this table is the tool for them.

Saying what you mean

Three tools make NULL behave the way the question needs

ToolUse it when
x IS NULL, x IS NOT NULLyou ask whether a value is missing
COALESCE(x, 0)a missing value means a known default
x IS DISTINCT FROM yyou want "different", with NULL treated as a value
SELECT COUNT(*) FROM returns WHERE refund IS DISTINCT FROM 12.00;  -- 4: T4 included

IS DISTINCT FROM is standard SQL and supported by DuckDB and SQLite (SQLite also writes it IS NOT). Name it as the clean answer to "not equal, missing included".

The classic trap

NOT IN with a NULL in the list keeps no row at all

Writtencode NOT IN ('R1', NULL)
→
Meanscode <> 'R1' AND code <> NULL
→
Becomessomething AND unknown: never true
Use NOT EXISTS when the list comes from a subquery that might contain a NULL.

The stretch of lab 2.2 shows it on the mini tables. In production it happens when a subquery returns a column with one missing value, and a report quietly goes empty.

Aggregates

Aggregates skip NULLs, except COUNT(*)

AVG divides 69.75 by the 4 known refunds. If an unknown refund should count as 0, the question wants AVG(COALESCE(refund, 0)) = 13.95.

The returns desk, 5 returns, one refund NULL (_tools/slide_examples.py).

Neither average is wrong: they answer different questions. The analyst's job is to know which one was asked.

Session 3

Grouping and having

  • Predict the number of rows a GROUP BY returns
  • Choose between WHERE and HAVING for a condition
  • Count distinct values inside a group
03
GROUP BY

GROUP BY changes the grain: one row per group

SELECT reason_code,
       COUNT(*)    AS returns,
       SUM(refund) AS refunds
FROM returns
GROUP BY reason_code;
reason_codereturnsrefunds
R1220.25
R2249.50
R31NULL

Five rows in, three out: one row per reason that occurs. R4 has no return, so no group.

Predict the number of output rows before running any GROUP BY: it is the number of distinct values of the grouping columns among the rows that pass WHERE.

R3's sum is NULL because its only refund is unknown.

The rule

After GROUP BY, SELECT may show only group columns and aggregates

Refused, or meaningless

SELECT reason_code, return_id, COUNT(*) ... GROUP BY reason_code: which of R1's two returns would the row show?

Fine

SELECT reason_code, COUNT(*), MAX(received_on) ... GROUP BY reason_code

Read it as "for each reason code, tell me ...". Anything else needs an aggregate.

DuckDB refuses the first query with a binder error that names the column. Read the message aloud: it tells you exactly which column to group by or aggregate.

WHERE or HAVING

WHERE filters rows before grouping; HAVING filters groups after

FROMreturns
→
WHERErefund IS NOT NULL
→
GROUP BYreason_code
→
HAVINGCOUNT(*) >= 2
→
SELECT, ORDER BY

Without the WHERE, the reasons with at least two returns are R1 and R2. A condition on a single row's value goes in WHERE; a condition on a count or a sum goes in HAVING.

Ask: with the WHERE in place, does the result change? (No: R1 and R2 each still have two known refunds.) Then ask what would change if T1's refund were NULL.

Counting things, not rows

COUNT(DISTINCT x) counts different values inside each group

ExpressionCountsReturns desk, all items
COUNT(*)rows8
COUNT(DISTINCT return_id)different returns5
COUNT(DISTINCT product_ref)different products5
What goes wrong. "How many customers ordered in May" with COUNT(*) counts orders.

Question 10 asks for both in one row per month: the number of orders and the number of different customers.

Groups of time

Group by an expression to get one row per month, week or band

SELECT CAST(date_trunc('week', received_on) AS DATE) AS week,
       COUNT(*) AS returns
FROM returns
GROUP BY week
ORDER BY week;
  • The expression in SELECT and in GROUP BY must be the same; the alias saves retyping it
  • In DuckDB date_trunc returns a timestamp, even on a DATE: cast it to DATE for a clean label

DuckDB accepts the alias in GROUP BY; some engines need the expression repeated. Both are correct SQL in DuckDB.

Session 4

Inner, outer, semi and anti joins

  • Predict the rows an inner and a left join return on small tables
  • Find rows without a partner with an anti join
  • Keep rows that have a partner without multiplying them, with a semi join
04
Inner join

An inner join keeps only the pairs of rows that match

SELECT t.return_id, i.result
FROM returns t
JOIN inspections i
  ON i.return_id = t.return_id;
-- 4 rows
  • T1 once, T2 twice, T5 once: 4 rows
  • T3 and T4 were never inspected: gone
  • The ON condition says which rows belong together
Two silent effects. Rows without a partner disappear; rows with several partners repeat.

Draw the two tables on the board and connect the matching rows with lines; count the lines. Every line is an output row.

Outer joins

A left join keeps every row of the left table, matched or not

return_idresult
T1pass
T2pass
T2fail
T3NULL
T4NULL
T5pass

returns LEFT JOIN inspections: 6 rows. The unmatched returns come back with NULL in every column of the right side. A right join keeps the right side; a full join keeps both.

The NULLs here mean "no partner", a fourth meaning of NULL on top of those of session 2.

Anti join

An anti join keeps the rows that have no partner

SELECT t.return_id
FROM returns t
WHERE NOT EXISTS (
  SELECT 1 FROM inspections i
  WHERE i.return_id = t.return_id
);
-- T3, T4
  • "Returns never inspected", "products never sold", "customers who never ordered"
  • Also written as a left join with WHERE i.return_id IS NULL
  • Avoid NOT IN (subquery): one NULL in it empties the result

NOT EXISTS reads like the question. The left-join form is common in older code; recognise both.

Semi join

A semi join keeps each row that has a partner, once

SELECT COUNT(*)
FROM returns t
WHERE EXISTS (
  SELECT 1 FROM inspections i
  WHERE i.return_id = t.return_id
);
-- 3

Not the same as an inner join

The inner join counted 4 rows: T2 twice. "How many returns were inspected?" is 3. EXISTS never repeats a row.

This is the bridge to Day 3: when the question is about the left table, filter with EXISTS rather than joining and then trying to undo the repeats.

Choosing

Choose the join from the question's words

The question saysJoin
"each ... with its ..."inner
"every ..., including those without ..."left
"... that never ...", "... without any ..."anti: NOT EXISTS
"... that had at least one ..."semi: EXISTS

Wrap-up

Three things to keep from Day 2

NULL is unknown

WHERE keeps only true rows. Ask IS NULL, or COALESCE on purpose.

Groups set the grain

One row per group; conditions on counts go in HAVING.

Joins drop and repeat
